# 帖子查询接口压测报告

## 一、测试目标

验证热门帖子详情接口（`GET /api/v1/posts/get/{postId}`）在引入 Redis 缓存策略（详情缓存 + 空值缓存 + 浏览量聚合）前后的性能对比，确认命中路径将 MySQL 读写完全挡掉后的 QPS 收益与延迟改善。

## 二、测试环境

| 项目 | 内容 |
| --- | --- |
| 应用地址 | http://localhost:8080 |
| 应用形态 | 旧代码基线：Docker 容器 campushub-app 与本地 jar 两种方式各测一轮；新代码：本地 jar（prod profile，环境变量指向容器化 MySQL/Redis/RabbitMQ） |
| 数据库 | MySQL 8.4（容器 campushub-mysql，宿主机端口 3307），campushub 库 |
| Redis | 7.4.11（容器 campushub-redis，宿主机端口 6380） |
| 帖子数据量 | 1,010,004 行（ch_post） |
| 压测目标帖 | postId = 1000000000000010000（热帖，改造前浏览量 886） |
| 压测工具 | JMeter 5.6.3（CLI 模式），脚本 JMeterTest/post-detail-bench.jmx |
| 耗时采集方式 | JMeter 聚合报告（jtl 全量分位数离线统计） |

## 六、结果分析

1. **吞吐量**：同口径对比（本地基线 vs 本地缓存后），QPS 从约 341（R1/R2 均值）提升至约 1185（R1/R3/R4 均值），**约 3.5 倍**。Docker 基线（约 326）与本地基线（约 341）量级一致，说明部署方式差异不影响结论。
2. **延迟**：平均值从约 167ms 降至约 49ms（下降约 71%）；基线 p99 出现 323~1199ms 的长尾（UPDATE 行锁竞争 + 刷脏），缓存后 p99 收敛至 119~172ms。
3. **DB 卸载**：命中路径零 DB 访问，DB 读写完全由缓存与聚合 Hash 承接。这正是设计目标——"DB 的读被缓存挡掉，DB 的写被聚合折叠"的前半句；后半句（flush 折叠落库）属后续任务。
4. **预热即巅峰**：缓存后预热轮 1578.9 QPS 略高于正式轮，因预热首请求回源写缓存后全部命中，正式轮受宿主机抖动影响在 1078~1278 区间波动。

## 七、结论

1. 缓存策略（详情缓存 + 空值缓存 + 浏览量 HINCRBY 记账）对热门帖子详情接口收益显著：**QPS 约 3.5 倍，平均延迟下降约 71%，命中路径 MySQL 读写归零**。
2. 空值缓存与写路径 DEL 失效经功能性验证正确：miss 回源 TTL 落在 300+random(0~120)s 区间；404 占位 TTL=60s；create/update/delete 后缓存与 DB 一致。
3. 遗留：浏览增量目前仅累计于 `campushub:post:view:delta`（无 TTL），flush 定时折叠落库为后续任务；未实现防击穿互斥锁（热键过期瞬间允许一小波并发回源，量级可接受）。

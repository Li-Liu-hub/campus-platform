# 商品冻结库存与购买记录状态方案

> 状态：**设计定稿，待开发**
> 适用模块：**仅 `campushub-shop`**（`ch_product` + `ch_user_product`）
> 不涉及：`campushub-order` 的 `ch_order`（业务模型不同，见 §2.3）
> 编写时间：2026-09-10

> 术语说明：本文的"购买记录"指店铺域的 `ch_user_product`，其 `order_status` 是该表自己的
> 状态列（0 待付款 / 1 已付款 / 2 已取消）。**与订单模块的 `ch_order` 没有任何关系**，
> 涉及表名处一律写明 `ch_user_product` 以免混淆。

---

## 1. 要解决的问题

### 1.1 现象

单件商品（校园二手小铺的常态，`product_stock = 1`）被买家拍下后：

- A 拍下不付款 → 库存被永久扣掉，商品显示"售罄"
- B 想买，看到的只有"没货"，无从判断"是卖完了"还是"正有人在付款、过一会儿可能放出来"
- A 最后也不付 → **这件东西谁都没买到**

### 1.2 三个根因

| 编号 | 根因 | 现状证据 |
| --- | --- | --- |
| R1 | 下单即**永久扣减**库存，没有"临时占用"这个中间态 | `ProductMapper.xml` 的 `deductStock` 直接 `product_stock = product_stock - n` |
| R2 | 购买记录**没有任何状态流转**，`order_status` 建单后永远是 0 | `UserProductController` 只有 create / query / get / delete，无付款、无取消 |
| R3 | 没有超时关闭机制，未付款的占用永不释放 | 全项目 `@Scheduled` 只有发件箱中继与帖子计数刷库，无购买记录超时任务 |

R1 决定"占用怎么记"，R2 + R3 决定"占用怎么还回去"。三者必须一起解决。

---

## 2. 方案选型

### 2.1 候选方案

| 方案 | 占用怎么表达 | 多件商品（stock > 1） | 是否引入"交易中"状态值 |
| --- | --- | --- | --- |
| A. 纯状态机 | `product_status = 2 交易中` | **表达不了**"3 件可卖 + 1 件冻结" | 引入 |
| B. 数量拆分 | `可卖量` / `冻结量` 两列 | 天然支持，部分冻结也能算清楚 | 由数量推导 |
| C. 状态机 + 数量拆分并行 | 两者都记 | 支持 | 引入 |

### 2.2 结论：选 B

**理由一：数量是粒度的真相，状态只能表达互斥的单一事实。**
多件商品"还有 3 件可卖、但有 1 件被冻结"是常态，状态字段无论是"在售"还是"交易中"都是错的。

**理由二："交易中"是可推导的，不该存。**
推导出来的东西存一份就是**第二处真相**，一旦两者不一致（状态说交易中、冻结量却是 0），排查极其痛苦。

**理由三：状态仍需保留，但只管它擅长的部分——生命周期。**
数量表达不了"卖家主动撤下"和"卖完了"的区别。这部分继续用现有的 `product_status`（1 上架 / 0 下架）。

> 一句话分工：**数量回答"能不能买"，状态回答"卖家还卖不卖"。**

### 2.3 边界声明：本方案不碰 `ch_order`

**店铺的购买记录走 `ch_user_product`，与 `campushub-order` 的 `ch_order` 无关。** 两者是不同的业务模型：

| 对比项 | `ch_user_product`（本方案） | `ch_order`（订单模块） |
| --- | --- | --- |
| 业务 | 在店铺里买商品 | 发布需求等人抢单 |
| 类型 / 角色 | 买家 + 商品所属店铺的卖家 | 发布者 `order_sent_user_id` + 接单者 `order_receive_user_id` |
| 订单类型 | 无类型，直接对应某个商品 | 跑腿代取 / 代买代购 / 其他互助 |
| 库存 | 有商品库存需要冻结与回补 | **没有库存概念**，超时只是关闭订单 |

所以本方案**只改 `campushub-shop`**，不改 `ch_order`、不动订单模块的任何代码。

> 附（仅供参考，不在本次范围）：排查中确实发现 `ch_order` 有同构的缺失——`order_timeout`
> 字段除被写入与返回外没有任何查询或定时任务读取它；状态 `3 已取消`（注释写"主动取消或
> 超时关闭"）也没有任何代码路径会设置。**但那是订单域自己的债**，应另开任务处理。

## 3. 表设计

### 3.1 `ch_product`（改后完整结构）

```sql
CREATE TABLE IF NOT EXISTS `ch_product`
(
    `product_id`              BIGINT         NOT NULL COMMENT '商品 ID',
    `product_shop_id`         BIGINT         NOT NULL COMMENT '所属店铺 ID',
    `product_name`            VARCHAR(128)   NOT NULL COMMENT '商品名称',
    `product_price`           DECIMAL(10, 2) NOT NULL COMMENT '商品价格',
    `product_stock`           BIGINT         NOT NULL DEFAULT 0 COMMENT '可卖库存，下单冻结时减少、取消或超时后回补、付款后不再回补',
    `product_stock_locked`    BIGINT         NOT NULL DEFAULT 0 COMMENT '冻结库存，已下单未付款占用中，付款后消耗',
    `product_status`          TINYINT        NOT NULL DEFAULT 1 COMMENT '上架状态：1 上架，0 下架',
    `product_idempotency_key` VARCHAR(64)    NOT NULL COMMENT '商品幂等键，由前端每次提交时生成并传递，防止重复创建商品',
    `product_is_delete`       TINYINT        NOT NULL DEFAULT 0 COMMENT '软删除标识：0 未删除，1 已删除',
    `create_time`             DATETIME       NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    `update_time`             DATETIME       NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
    PRIMARY KEY (`product_id`),
    UNIQUE KEY `uk_product_idempotency_key` (`product_idempotency_key`),
    INDEX `idx_shop_status` (`product_shop_id`, `product_status`),
    INDEX `idx_delete_time` (`product_is_delete`, `create_time`),
    CONSTRAINT `ck_product_stock_not_negative`
        CHECK (`product_stock` >= 0 AND `product_stock_locked` >= 0)
)
```

**变更点**：
1. 新增 `product_stock_locked`（冻结量）
2. `product_stock` 注释明确为"可卖量"（**列名不变**，避免改动现有引用）
3. 新增 `ck_product_stock_not_negative` 兜底约束

**刻意不加的东西**：
- 不加"总量"列。`总量 = 可卖 + 冻结` 可推导，存下来就是第三处维护点，三方对不上时无法判断谁错。
- 不加 `order_id` 之类的"当前占用者"引用。占用关系由 `ch_user_product` 表达，否则商品与购买记录形成双向依赖。
- `product_status` 不加"交易中"、不加"已售出"。

### 3.2 `ch_user_product`（改后完整结构）

```sql
CREATE TABLE IF NOT EXISTS `ch_user_product`
(
    `user_product_id`              BIGINT      NOT NULL COMMENT '用户购买商品记录 ID',
    `user_id`                      BIGINT      NOT NULL COMMENT '购买用户 ID',
    `product_id`                   BIGINT      NOT NULL COMMENT '商品 ID',
    `product_number`               BIGINT      NOT NULL COMMENT '购买数量',
    `purchase_time`                DATETIME    NOT NULL COMMENT '下单时间',
    `payment_time`                 DATETIME             COMMENT '付款时间，付款成功时回填',
    `order_status`                 TINYINT     NOT NULL DEFAULT 0 COMMENT '购买记录状态：0 待付款，1 已付款，2 已取消',
    `user_product_idempotency_key` VARCHAR(64) NOT NULL COMMENT '下单幂等键，由前端每次提交时生成并传递，防止重复下单导致重复冻结库存',
    `create_time`                  DATETIME    NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    `update_time`                  DATETIME    NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
    PRIMARY KEY (`user_product_id`),
    UNIQUE KEY `uk_user_product_idempotency_key` (`user_product_idempotency_key`),
    INDEX `idx_user_id` (`user_id`, `create_time`),
    INDEX `idx_product_id` (`product_id`),
    INDEX `idx_status_create` (`order_status`, `create_time`)
)
```

**变更点**：
1. `payment_time` 注释修正：原写"预约付款时间"，实际应为"付款时间"（付款成功时回填）
2. 新增 `idx_status_create (order_status, create_time)` —— 超时任务扫描必需。现有 `idx_user_id`、`idx_product_id` **都无法支撑** `WHERE order_status = 0 AND create_time < ?`，不补索引任务一上线就是全表扫。

### 3.3 升级脚本

已有环境的升级脚本另存为 `campushub-shop/src/main/resources/db/stock_locked_upgrade_20260910.sql`：

```sql
ALTER TABLE `ch_product`
    MODIFY COLUMN `product_stock` BIGINT NOT NULL DEFAULT 0
        COMMENT '可卖库存，下单冻结时减少、取消或超时后回补、付款后不再回补';

ALTER TABLE `ch_product`
    ADD COLUMN `product_stock_locked` BIGINT NOT NULL DEFAULT 0
        COMMENT '冻结库存，已下单未付款占用中，付款后消耗'
        AFTER `product_stock`;

ALTER TABLE `ch_product`
    ADD CONSTRAINT `ck_product_stock_not_negative`
        CHECK (`product_stock` >= 0 AND `product_stock_locked` >= 0);

ALTER TABLE `ch_user_product`
    MODIFY COLUMN `payment_time` DATETIME NULL COMMENT '付款时间，付款成功时回填';

ALTER TABLE `ch_user_product`
    ADD INDEX `idx_status_create` (`order_status`, `create_time`);
```

新增列有默认值 0，存量行自动填充，无需回填数据。

### 3.4 字段职责表

| 字段 | 谁写 | 含义 |
| --- | --- | --- |
| `product_stock` | 下单 / 取消 / 超时 / 卖家补货 | 现在能卖出去的数量 |
| `product_stock_locked` | 下单 / 付款 / 取消 / 超时 | 已被人占着、还没付款的数量 |

| `order_status` | 下单 / 付款 / 取消 / 超时 | 0 待付款 / 1 已付款 / 2 已取消 |
| `payment_time` | 付款 | 实际付款时刻 |

## 4. 展示态推导

查询商品时由已有字段推导，**不落库**。`ProductVO` 直接返回 `productStock` 与 `productStockLocked` 两个原始数字，展示方式交给前端（"可卖 3 件" 或 "可卖 3 件（1 件交易中）" 都能实现）。

后端同时返回一个推导出的枚举字段，供前端做统一判断：

| 判断顺序 | 条件 | 展示态 | 文案建议 |
| --- | --- | --- | --- |
| 1 | `product_is_delete = 1` | 已删除 | 不返回 |
| 2 | `product_status = 0` | 已下架 | 卖家已下架 |
| 3 | `product_stock > 0` | 可购买 | 剩余 N 件 |
| 4 | `product_stock = 0 AND product_stock_locked > 0` | **交易中** | 有人在付款中，可稍后再看 |
| 5 | `product_stock = 0 AND product_stock_locked = 0` | 已售罄 | 已售罄 |

判断顺序不可调换：已下架优先级高于库存状态，否则卖家撤下的商品会显示成"可购买"。

## 5. 功能流程

### 5.1 下单（现有接口 `POST /api/v1/user-products/create`，语义变更）

| 步 | 动作 | 说明 |
| --- | --- | --- |
| 1 | 校验登录、商品存在且在售 | 商品已下架 → 409 |
| 2 | 插入购买记录（状态 0，带幂等键） | 唯一键冲突 → 回查原记录返回，**直接结束，不冻结库存** |
| 3 | 冻结库存（一条语句同时改两列） | 影响 0 行 → 抛 409，事务回滚第 2 步 |
| 4 | 返回购买记录 | |

```sql
-- 步 3：冻结
UPDATE ch_product
SET product_stock        = product_stock - #{number},
    product_stock_locked = product_stock_locked + #{number}
WHERE product_id = #{productId}
  AND product_status = 1
  AND product_stock >= #{number}
```

- 影响 1 行 → 成功
- 影响 0 行 → 已下架或可卖量不足 → 409

**事务边界**：步 2 + 步 3 必须同一事务（`@Transactional`）。步 3 失败要连带回滚步 2，否则留下没有库存支撑的记录。

**步 2 与步 3 的顺序不可调换**：先插记录是为了让唯一索引先拦住重复提交，此时尚未冻结任何库存，重复请求天然安全。

### 5.2 付款（新增 `POST /api/v1/user-products/pay/{userProductId}`）

| 步 | 动作 | 说明 |
| --- | --- | --- |
| 1 | 抢占购买记录状态 | 条件更新，**抢到了才继续** |
| 2 | 消耗冻结量 | 不回补可卖量 |
| 3 | 返回购买记录 | |

```sql
-- 步 1：抢状态（0 待付款 → 1 已付款）
UPDATE ch_user_product
SET order_status = 1, payment_time = NOW()
WHERE user_product_id = #{id}
  AND user_id = #{currentUserId}
  AND order_status = 0

-- 步 2：消耗冻结量
UPDATE ch_product
SET product_stock_locked = product_stock_locked - #{number}
WHERE product_id = #{productId}
  AND product_stock_locked >= #{number}
```

- 步 1 影响 0 行 → 已被取消或被超时任务关闭（或不是自己的记录）→ 409，**不得动库存**
- 步 2 影响 0 行 → 冻结量对不上，数据已不一致 → 抛异常回滚 + error 日志告警

**付款与取消的分水岭**：付款只减冻结量，**不回补**可卖量——货真的卖掉了，是消耗不是归还。

### 5.3 买家主动取消（新增 `POST /api/v1/user-products/cancel/{userProductId}`）

| 步 | 动作 | 说明 |
| --- | --- | --- |
| 1 | 抢占购买记录状态 | `0 待付款 → 2 已取消` |
| 2 | 解冻（回补） | 冻结量减、可卖量加 |
| 3 | 返回 | |

```sql
-- 步 1
UPDATE ch_user_product
SET order_status = 2
WHERE user_product_id = #{id}
  AND user_id = #{currentUserId}
  AND order_status = 0

-- 步 2：解冻
UPDATE ch_product
SET product_stock_locked = product_stock_locked - #{number},
    product_stock        = product_stock + #{number}
WHERE product_id = #{productId}
  AND product_stock_locked >= #{number}
```

权限：**只能取消自己的、且只能取消待付款的记录**。已付款的不许自行取消。

### 5.4 超时自动关闭（定时任务，无接口）

与 5.3 完全相同的两步逻辑，只是触发者变成定时任务，且条件里不带 `user_id`：

```sql
-- 扫描候选（走 idx_status_create）
SELECT * FROM ch_user_product
WHERE order_status = 0
  AND create_time < NOW() - INTERVAL #{timeoutMinutes} MINUTE
ORDER BY create_time ASC
LIMIT #{batchSize}
```

逐条按 5.3 的两条 SQL 处理，**每条各自成事务**。

### 5.5 卖家查看"谁在付款中"（新增 `GET /api/v1/products/{productId}/pending-purchases`）

| 步 | 动作 |
| --- | --- |
| 1 | 校验当前登录用户是商品所属店铺的店主，否则 403 |
| 2 | 查该商品 `order_status = 0` 的购买记录，按创建时间倒序游标分页 |
| 3 | 只返回必要字段：买家用户 ID、购买数量、下单时间、超时时刻 |

**隐私边界**：只暴露买家 ID 与交易必要信息，不返回联系方式。卖家要联系买家应走站内其他渠道。

## 6. 竞态与事务

### 6.1 付款与超时任务的竞争

用户在超时任务关闭购买记录的同一瞬间点了付款。**以 `ch_user_product.order_status` 的条件更新决出胜负**（见 5.2 / 5.3 的步 1）。

**关键顺序：先抢记录状态，抢到了才动库存。** 反过来写会在竞争失败时误扣库存。
两次状态抢占都只可能有一方成功——`order_status = 0` 这个条件在行锁内被判定，天然互斥。

### 6.2 事务边界

- 下单：`@Transactional`（插记录 + 冻结）
- 付款：`@Transactional`（抢状态 + 消耗冻结）
- 取消：`@Transactional`（抢状态 + 解冻）

库存那步影响 0 行（数据不一致）时抛异常，让状态变更一起回滚，避免留下"已付款但冻结量没消耗"的脏数据。

## 7. 超时任务设计

新建 `campushub-shop/src/main/java/com/campushub/shop/task/PurchaseTimeoutCloseTask.java`，风格对齐现有 `campushub-post/task/ViewCountFlushTask.java`。

| 项 | 取值 | 说明 |
| --- | --- | --- |
| 扫描间隔 | `campushub.shop.timeout-scan-interval-ms`，默认 60000 | 与现有 `fixedDelayString` 写法一致 |
| 超时时长 | `campushub.shop.order-timeout-minutes`，默认 15 | 配置化，演示时调 5 分钟即可验证 |
| 单批条数 | `campushub.shop.timeout-batch-size`，默认 200 | 避免一次锁太多行 |

两条硬约束：

1. **逐条处理，不用批量 UPDATE。** 每条都要"改状态 + 回补库存"两步且各自成事务。批量改状态后逐一回补，中途失败会留下已取消但没回补的记录，而这类损失是静默的（库存凭空少一件）。
2. **任务不能失败即止。** 单条处理抛异常时记日志并跳过，继续处理剩余记录；下一轮扫描会自然重试（因为状态仍是 0）。

## 9. 边界与风险

1. **软删除商品与未完成购买记录**：卖家删除商品时，若存在 `order_status = 0` 的记录，应先拒绝删除（或强制取消该购买记录并回补）。否则冻结量永远挂在一个不可见的商品上，账目无法收敛。
2. **幂等键与状态的关系**：重复提交返回原记录时**不得再次冻结库存**（首次已冻结）。现有"插记录失败即提前返回"的顺序天然正确，改动时需保持。
3. **冻结量的归还对象只有一个**：取消/超时回补到可卖量，付款消耗掉。不存在第三条路。
4. **`product_number` 上限**：现在只有 `@Min(1)`。单件商品若被传 `number = 5`，冻结会因可卖量不足而失败——行为正确，错误信息应明确是"库存不足"。
5. **`CHECK` 约束的兼容性**：MySQL 8.0.16 起才真正生效，8.4 无问题；若将来降级到 5.7 会被静默忽略。
6. **冻结量不接受卖家手工调整**：卖家的 `adjustStock` 只动可卖量。冻结量是系统占用，卖家能改就会破坏账目一致性。

## 10. 决策记录（2026-09-10 确认）

| 事项 | 决策 |
| --- | --- |
| 占用怎么表达 | 数量拆分（可卖量 + 冻结量），**不引入"交易中"状态值** |
| 只加几列 | **只加 `product_stock_locked` 一列**，不存"总量" |
| 买家能否主动取消 | **可以**，新增 `POST /cancel/{id}`，仅限自己的、待付款的 |
| 卖家能否看到"谁在付款中" | **可以**，新增按商品查待付款记录的接口，仅店主可查，只暴露必要字段 |
| 多件商品部分冻结如何展示 | 接口返回两个原始数字 + 展示态枚举，**两种展示方式都支持**，前端自选 |
| 超时时长 | **配置化**，默认 15 分钟（演示可调 5 分钟） |
| `ch_order` 的超时关闭 | **不在本次范围**，订单域自己的债，另开任务 |

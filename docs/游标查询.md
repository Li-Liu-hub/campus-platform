# 游标查询改造与压测记录

## 一、改造方案

### 1.1 为什么要做

原查询接口 `GET /api/v1/posts/query` 没有分页，一次返回全部匹配帖子，压测暴露出两个问题（数据见下文）：

- 单个响应约 **2MB**，带宽和 JSON 序列化先于数据库达到瓶颈，QPS 卡在 40 以下；
- 传统 `LIMIT offset, size` 分页在深翻页时要读取并丢弃前 offset 行，越翻越慢，IO 无解。

### 1.2 游标分页设计

用"上一页最后一行的排序键"定位下一页起点，每页成本恒定：

```sql
WHERE post_is_delete = 0
  AND (create_time < #{cursorTime} OR (create_time = #{cursorTime} AND post_id < #{cursorId}))
ORDER BY create_time DESC, post_id DESC
LIMIT #{pageSize}
```

设计要点：

- 排序键为二元组 `(create_time, post_id)`：`post_id` 决胜同一秒内的多条帖子，保证翻页边界不丢行、不重行；
- 依赖联合索引 `idx_delete_time (post_is_delete, create_time)`：InnoDB 二级索引叶子隐式携带主键，`ORDER BY create_time, post_id` 天然被索引序满足，免 filesort；
- 接口契约：响应携带 `hasMore`，为 true 时返回 `nextCursorTime` / `nextCursorId`，前端翻页原样回传，首页不传游标；
- `pageSize` 缺省 20，上限 100；
- 游标只用于主信息流；标题前缀搜索保留在条件查询里（`LIKE 'x%'` 可走 range），深分页类需求不做。

## 二、压测环境与方法

| 项 | 值 |
|---|---|
| 被测应用 | CampusHub（Docker 容器 campushub-app，内嵌 Tomcat 默认线程池 max=200） |
| 数据库 | MySQL 8.4（Docker，与服务器同机） |
| 数据规模 | 约 1 万条种子帖子（`/create` 接口 + `${__UUID()}` 幂等键灌入） |
| 压测工具 | JMeter 5.6.3 GUI 模式，与服务器同机（8 核 16 线程笔记本） |
| 压测接口 | `GET /api/v1/posts/query`，不带任何条件（最坏情况：全量查询） |
| 压测参数 | 线程组 Ramp-Up 1s，循环"永远"，调度器控制持续时长；每轮开始前清空聚合报告 |

**基线时的表结构状态**：`ch_post` 仅有主键和幂等键唯一索引，无任何业务二级索引；SQL 无 LIMIT。

## 三、基线数据（优化前）

### 轮次 1：短脉冲（约 1 秒，60 样本）

| 指标 | 值 |
|---|---|
| 样本数 | 60 |
| 平均值 | 471 ms |
| 中位数 | 57 ms |
| 90% / 95% / 99% 百分位 | 952 / 955 / 957 ms |
| 最小 / 最大 | 32 / 958 ms |
| 异常% | 0.00% |
| 吞吐量（QPS） | **59.1 /sec** |
| 接收流量 | 128697.88 KB/sec |

推导：单响应平均大小 = 128697.88 ÷ 59.1 ≈ **2177 KB ≈ 2.1 MB**。

**结论**：1 秒脉冲中一半请求排队前就被服务（中位数 57ms），另一半全部卡在 ~950ms。脉冲持续时间太短，排队尚未发酵，59 QPS 属于虚高，不能当容量。

### 轮次 2：30 线程持续 10 秒（基线正式值）

| 指标 | 值 |
|---|---|
| 样本数 | 354 |
| 平均值 | 421 ms |
| 中位数 | 29 ms |
| 90% / 95% / 99% 百分位 | 901 / 1044 / 1978 ms |
| 最小 / 最大 | 11 / 2009 ms |
| 异常% | 0.00% |
| 吞吐量（QPS） | **39.0 /sec** |
| 接收 / 发送流量 | 77858.81 / 11.75 KB/sec |

推导：单响应平均大小 = 77858.81 ÷ 39.0 ≈ **1996 KB ≈ 2.0 MB**。

**结论**：

- 持续压测的容量约 **39 QPS**，比脉冲的 59 低——短脉冲会虚高，持续施压才见真实容量；
- 响应时间两极分化（中位数 29ms vs 90 分位 901ms）是典型的排队特征：一半请求秒回，四成在连接池/数据库处理链路上排队 1~2 秒；
- 响应时间均值 421ms、QPS 39，按 Little's Law 折算平均在途并发 ≈ 39 × 0.421 ≈ 16，与 30 线程中排队等待的比例吻合。

### 轮次 3：60 线程（失败记录，数据作废）

现象：

- JMeter GUI 直接卡死（标题栏"未响应"），本轮数据不可信；
- 应用日志爆发 `AsyncRequestNotUsableException: ... Broken pipe`（服务端写 2MB 响应途中客户端断开）；
- Tomcat 工作线程膨胀到 167 号（`o-8080-exec-167`，接近默认上限 200）。

原因链：60 线程 × 2MB 响应 ≈ 80MB/s 数据灌入 JMeter → 查看结果树囤积响应体撑爆默认 1GB 堆 → Full GC 窒息 → GUI 线程饿死；10 秒调度器到点强停时掐断在途连接，服务端写 socket 报 Broken pipe。

**结论**：胖响应先压死了测量工具。教训：结果树必须禁用、HEAP 调大、60+ 线程用命令行模式（`jmeter -n`）。

## 四、基线归因

| 层 | 问题 | 证据 |
|---|---|---|
| SQL 层 | 无 LIMIT 全量返回；`ch_post` 无业务二级索引，`type=ALL` + filesort | EXPLAIN（待补图） |
| 传输层 | 单响应 ~2MB，序列化 + 传输占用线程时间 | 接收流量 ÷ 吞吐量 ≈ 2MB/次 |
| 排队层 | RT 两极分化，90 分位进入秒级 | 中位数 29ms vs 90% 901ms |

**优化动作**：联合索引 `idx_delete_time` + 游标分页改造（本次），预期响应瘦到 ~20KB、QPS 数倍提升。

## 五、改造后对照（30 线程档）

改造内容：`idx_delete_time` 索引 + 游标分页（见第一节）。同条件复测：30 线程 × 10 秒，接口带 `pageSize=20`。

| 指标 | 基线（无分页） | 游标分页（索引未上） |
|---|---|---|
| 样本数（10s） | 354 | 1530 |
| 吞吐量 QPS | 39.0 | **167.5** |
| 平均值 | 421 ms | 119 ms |
| 中位数 | 29 ms | 105 ms |
| 90% / 95% / 99% 百分位 | 901 / 1044 / 1978 ms | 228 / 249 / 289 ms |
| 最小 / 最大 | 11 / 2009 ms | 6 / 330 ms |
| 异常% | 0.00% | 0.00% |
| 单响应大小 | ~2.0 MB | **~2.6 KB** |

**游标轮结论**（索引未上）：QPS 提升 4.3 倍，单响应从 2.0MB 缩至 2.6KB，99 分位从 1978ms 降至 289ms。中位数从 29ms 变为 105ms 属正常：基线时一半请求恰好躲开排队被秒回（病态两极分布），游标版全链路均匀变快，评估以吞吐量和 90/99 分位为准。

**注**：请求总数从 354 涨到 1530 并非异常——"循环：永远"下每线程发完即刻发下一个，总请求数 ≈ 并发 × 时长 ÷ 平均响应时间，响应变快后同样时长自然容纳更多请求。

索引落地后的 A/B 对照实验升到 60 线程、改用 CLI 模式进行（样本更多、无 GUI 干扰），见第六节。

## 六、60 线程 CLI 压测矩阵：索引 A/B 实验

环境：JMeter 5.6.3 命令行模式（`jmeter -n`），无 GUI、无结果树、禁用 KeepAlive，`pageSize=20`，全部 60 线程 × 10 秒。数据量 10004 行（全部未删除）。E2/E3 各复测一轮以评估机器噪声。

| 实验 | 条件 | idx_delete_time | 样本 | QPS | 平均 | 中位 | p90 | p99 | 错误 |
|---|---|---|---|---|---|---|---|---|---|
| E1 | 无参数 | 有 | 3511 | 354.2 | 164 | 165 | 193 | 319 | 0 |
| E2 | postType=二手闲置 | **无** | 8064 | 819.3 | 71 | 70 | 88 | 108 | 0 |
| E2b | postType=二手闲置（复测） | **无** | 4459 | 448.5 | 129 | 128 | 161 | 273 | 0 |
| E3 | postType=二手闲置 | 有 | 4321 | 436.2 | 133 | 135 | 153 | 260 | 0 |
| E3b | postType=二手闲置（复测） | 有 | 4012 | 404.4 | 143 | 143 | 178 | 291 | 0 |

响应字节数（JMeter bytes 列口径）：E1 ≈ 4865 B，E2/E3 ≈ 4778 B，差异可忽略。

EXPLAIN 验证：有索引时两条 SQL 均命中 `idx_delete_time`（type=ref，Backward index scan，无 filesort），执行计划正确。

### 结论

1. **同配置复测吞吐差 83%（E2 819 vs E2b 448）**：应用、MySQL、JMeter 共享一台 8 核笔记本，单轮压测噪声远大于索引收益——**单轮数据不能下结论，必须复测**；
2. **E2b vs E3b（448 vs 404，差异 ±10%）**：1 万行数据量下，索引对该查询的收益被噪声淹没——热 buffer pool 里的全表扫描也只有十几毫秒，两条访问路径都足够快；
3. **索引的价值是"防未来"**：全表扫描成本随数据量线性增长，索引路径近乎恒定。EXPLAIN 已证明计划正确，万级数据是"太小的战场"，测不出它的价值——这不等于索引白建；
4. **CLI 60 线程全部 0 错误**：GUI 时代的 60 线程卡死与 23% 异常在干净环境不复现，确认为测量端问题（结果树囤积 + 报告未清空混入脏数据），非服务端缺陷；
5. **当前瓶颈不在 SQL 访问路径**：E1 与 E3 同在噪声范围内，继续压榨需换战场（缓存、连接池参数、序列化），或加大数据量后再验证索引收益。

## 七、百万行验证：JOIN 劣化、索引 A/B 与修复全过程

数据量从 1 万行灌到 **101 万行**（`JMeterTest/seed-1m.sql`，990k 行 22 秒），压测配置不变（60 线程 × 10 秒，CLI）。这一节是整个调优故事的高潮，包含一次真实的事故定位。

### 7.1 事故：百万行下所有请求退化到 6 秒

灌数后第一次压测（E4 初版）：平均 **26.5 秒**、33% 超时。定位链条（每一环都有工具背书）：

1. 应用内埋的 StopWatch 显示 6.3s 花在 `postMapper.selectByCondition`；
2. 但同一时刻在 MySQL 容器内直接执行同一条 SQL：**0.9ms**（EXPLAIN ANALYZE 实测）；
3. general log 抓取应用发出的原封 SQL，对比发现差异——**应用版本带 `LEFT JOIN ch_user`**；
4. 复现测试：无 JOIN 的 SQL 1ms，带 JOIN 的同一条 **5.9s**（百万行下 JOIN 使优化器放弃索引序，退化为 join buffer + 全表排序；MySQL 8 的 hash join 是默认行为）；
5. 修复：查询列表里的 `u.user_nickname` **从未被映射到 PostVO/实体**（死列），直接删除 JOIN；若将来需要昵称，用"子查询先截断 20 行再关联"或冗余作者快照，绝不在分页扫描里 JOIN；
6. 兜底保险：XML 加 `/*+ NO_BNL(u) */` 提示禁用 hash join（实测提示版 1.7ms vs 无提示 5.9s）。

修复验证：单请求 **5.8s → 13~18ms**。

**调试副产品的教训：Docker 构建上下文陈旧**。修复代码后 `docker compose build`（含 `--no-cache`）三次重建，应用行为始终不变——general log 证明容器里跑的仍是最老版本 SQL。最终用宿主机 `mvn package` + `docker cp` 直换 jar 才让修复生效。Docker Desktop 在 Windows 上的文件同步存在陈旧快照问题，遇到"改了代码行为不变"先怀疑这个，重启 Docker Desktop 可解。

### 7.2 百万行索引 A/B 矩阵（60 线程 × 10 秒）

| 实验 | 条件 | 索引 | 样本 | QPS | 平均 | 中位 | p90 | p99 | 错误 |
|---|---|---|---|---|---|---|---|---|---|
| E4 | 无参数 | (is_delete, create_time) | 9037 | **911.0** | 63 | 60 | 90 | 137 | 0 |
| E5 | postType 筛选 | (is_delete, create_time) | 538 | 54.9 | 1123 | 1189 | 1245 | 1300 | 0 |
| E6 | postType 筛选 | **无** | 70 | 9.1 | **25453** | 29482 | 37210 | 37213 | **14.3%** |
| E7 | postType 筛选 | (is_delete, **post_type**, create_time) | 11319 | **1142.5** | 50 | 47 | 72 | 101 | 0 |

### 7.3 结论

1. **无索引百万行 = 生产事故**（E6）：9 QPS、25 秒、14% 错误，Tomcat 线程与连接池全面排队——第一、二节预言的雪崩链完整上演；
2. **"过滤列必须进索引"**：`idx_delete_time` 不含 post_type，筛选只能靠回表逐行验证（E5，1123ms）；把 post_type 纳入联合索引后过滤在索引内完成（E7，50ms）——**同一条 SQL，索引列序不同差 20 倍**；
3. **E7 vs E6 差 125 倍**：这就是"联合索引能跨表吗"那场讨论的最终答案——索引由查询的过滤+排序模式决定，`(post_is_delete, post_type, create_time)` 与游标 SQL 逐列吻合；
4. **两把索引各司其职**：无参数信息流走 `idx_delete_time`（911 QPS），分类筛选走 `idx_type_time`（1143 QPS），百万行下双双稳定；
5. **关于"100ms 算快吗"**：60 线程饱和压测下的 100ms 与单人闲时不可同日而语；单发实测 13~18ms。压测数字要带着并发语境读。

## 八、压测过程踩坑记录

1. **KeepAlive 陈旧连接**：两轮压测间隔后复用已断开的连接，报 `NoHttpResponseException: failed to respond`——HTTP 请求关掉"使用 KeepAlive"后消失；
2. **token 会话被顶**：`max-login-count=3` + `overflow-logout-mode=REPLACED`，多次登录后最早的 token 失效，压测报 401——重新登录取最新 token；
3. **聚合报告是累积统计**：换线程数前必须 Ctrl+E 清空，否则各档数据互相污染；
4. **平均值会骗人**：两极分布下平均值毫无意义，结论只看中位数和 90/99 百分位；
5. **GUI 模式只适合调试**：压测时禁用查看结果树；大规模压测用 `jmeter -n -t 计划.jmx -l result.jtl`；
6. **CLI 模式解放 60 线程**：无 GUI、无结果树囤积，60 线程跑满 10 秒 0 错误（见第六节）——此前卡死与 23% 异常均为测量端问题；
7. **同配置必须复测**：同一份 JMX 两轮吞吐 819 vs 448（差 83%）——共享机器上单轮结论不可靠，至少取两轮对比再下结论；
8. **Docker 构建上下文会陈旧**：改了 XML 后 `docker compose build`（含 `--no-cache`）三次都不生效，general log 抓包确认容器仍在跑最老版本 SQL。最终 `mvn package` + `docker cp` 直换 jar 生效。Docker Desktop 的 Windows 文件同步存在陈旧快照问题，"改了代码行为不变"时先重启 Docker Desktop 再排查代码；
9. **JMeter `-l` 指向已存在的 jtl 会追加而非覆盖**：换实验前必须删除旧结果文件，否则两轮数据混在一份报告里（本次 60 旧样本 + 70 新样本混出 130 的假象）。

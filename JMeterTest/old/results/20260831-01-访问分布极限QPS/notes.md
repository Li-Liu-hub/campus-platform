## 计数器差分

窗口 = 确认级 warmup + 3 轮（Grab run1-before 在 warmup 之前），请求数含 warmup；差分除以窗口请求数：

| arm | 窗口请求 | MySQL Com_select/请求 | Redis cmd/请求 | Redis hits/请求 | Redis misses/请求 |
|---|---|---|---|---|---|
| hot-single | 344619 | 0.00002 | **3.00** | 2.00 | 0 |
| mixed-80-20 | 320547 | 0.146 | **3.15** | 1.85 | 0.146 |
| cold-all | 221098 | 0.993 | **4.06** | 1.05 | 0.993 |

- hot-single：MySQL Com_select 差分仅 5 次（34 万请求）→ **命中路径 MySQL 读归零**，最硬证据成立；
- cold-all：每请求 1 次 miss + 1 次回源 SELECT（0.993/0.993），全冷语义成立；
- mixed：冷请求实际占比 14.6%（线程占比 20%，冷路径单线程吞吐低于热路径所致），每冷请求恰好 1 miss + 1 SELECT。

## 结论

- 预期 vs 实测：
  - 绝对值判据三项全部未达：hot 4185.2 < 4500（-7%）、mixed 4044.0 < 4200（-3.7%）、cold 2803.7 < 3300（-15%）；
  - 机制判据全部吻合：每请求 Redis 命令数实测 3.00 / 3.15 / 4.06，与假设的 3 / 3.2 / 4 一致；MySQL 卸载证据（hot Com_select ≈ 0）成立；错误率全 0 成立。
- 差异归因：
  1. 绝对值整体下移是宿主机状态漂移：同一 commit、同参数（60 线程热读）在前序实验实测 5062，本轮扫描 4798.8、确认轮 4185.2——跨时段绝对值不可比，同实验内三场景相对关系有效；
  2. hot 与 mixed 接近（4185 vs 4044）而非假设的线性下移：混合场景冷组线程少（12/60）且实际冷请求占比仅 14.6%，总吞吐由热路径主导；两者共同的天花板并非纯 Redis 命令速率（若为命令速率，hot 应 ≈15000/3 = 5000），而是宿主机 CPU / Tomcat / 日志 I/O 的复合上限；
  3. cold 拐点线程数（100）高于 hot（60）：冷路径含 DB 回源等待，线程等 DB 期间不占 Redis 连接，需要更高并发才能喂满瓶颈，且冷路径本身多一条 SET 写回命令。
- 执行偏差记录（不影响正式数据）：
  1. 第一次 cold/mixed 确认轮被污染（hits/req 2.7 暴露）：JMeter CLI 每次新进程会重置 CSV 游标，确认轮从头读已缓存 ID 段变"温读"——已按 fresh ID 段（切分文件逐轮注入 -JcsvFile）重跑修正，修正后 misses/req 0.993 验证冷读语义；
  2. JMeter CLI 的 stdout 被 PowerShell `Select-String` 过滤时 jmeter.bat 会被提前终止（0 样本/退出码 1），改用 `Select-Object -Last N` 全量消费后稳定；
  3. JMeter `-l` 对已存在 jtl 是追加，hot scan-30 与两 arm 的 warmup 出现双份样本——扫描值以当时 summary 为准（scan-30 = 4374.1），确认轮数据用时间戳过滤后统计，不受影响。

## 下一步动作

2. 跨实验对比必须同时段同环境跑基线与对照（本次 5062 → 4185 的漂移即反例）；
3. cold-all 场景可作为 flush 任务落地后的回归场景：验证折叠落库不侵占读路径吞吐。

# 订单并发抢单-100线程1轮-20260901222300

## 一、跑前假设与可量化判据（跑后不回改）

功能正确性验证（非性能对照实验），验证目标：分布式锁 + 数据库状态条件更新兜底下的抢单互斥。

**假设**：100 线程并发抢同一待接单订单时，Redis 锁（HSETEX FNX EX）串行化竞争请求，
数据库 `WHERE order_status = 0` 条件更新兜底，最终恰有一人接单成功。

**可量化判据**（每轮）：
1. JTL 中 HTTP 200 恰好 1 个，其余全部 409；
2. MySQL 该订单 `order_status = 1` 且 `order_receive_user_id` 非空（唯一一行）；
3. 抢单结束后 Redis 锁键 `campushub:order:lock:{orderId}` 不存在（已释放）；
4. 锁超时自动释放：字段级 TTL 到期后键自动消失（HTTL 可观测）。

**锁设计**（[DistributedLockServiceImpl.java](../../campushub-infrastructure/src/main/java/com/campushub/infrastructure/redis/impl/DistributedLockServiceImpl.java)）：

- 锁结构为 Hash，字段名 = 持有者唯一 token（UUID），字段值固定 "1"；
- 获取锁 = `HSETEX key FNX EX 10 FIELDS 1 {token} 1`（Redis 8.0 内置原子命令：字段不存在才写入并带字段级 TTL）；
- 释放锁 = `HGETDEL key FIELDS 1 {token}`（内置原子"读+删"；字段名即自身 token，不可能误删他人锁）；
- 超时自动释放 = 字段级 TTL 10 秒，持锁业务超时未释放时由 Redis 自动删除字段兜底；
- 数据库兜底 = `casGrab`：`UPDATE ch_order SET order_status=1, order_receive_user_id=? WHERE order_id=? AND order_status=0 AND order_is_delete=0`，
  行锁 + 状态条件保证并发下仅一人更新成功，Redis 故障时降级直走该更新，正确性不受影响。

## 四、锁 TTL 超时自动释放验证（redis-cli）

```text
HSETEX lock:ttl-demo FNX EX 2 FIELDS 1 tok 1  -> (integer) 1   # 获取成功
HTTL   lock:ttl-demo FIELDS 1 tok             -> (integer) 2   # 字段级 TTL 生效
（等待 3 秒）
EXISTS lock:ttl-demo                          -> (integer) 0   # 键随字段过期自动消失
```

持锁方未调用释放时，锁在 TTL 到期后被 Redis 自动删除，不会死锁。

## 六、结论

**预期 vs 实测**：预期"每轮恰好 1 个 200、99 个 409，DB 唯一接单人，锁键释放"——
3 轮实测全部命中判据 1~3；判据 4（TTL 自动释放）经 redis-cli 独立验证成立。

**多源证据差分**：客户端侧每轮 200/409 = 1/99；MySQL 侧每轮订单恰一行且 status=1、
receive_user_id 非空；Redis 侧锁键 EXISTS=0（无残留）。三方一致，无超发。

**已知局限**：

1. 闭环（closed-loop）压测存在协调遗漏（coordinated omission），延迟指标偏乐观，
   本次只取量级不作为性能结论；
2. 100 线程仅轮换 20 个真实用户 token，未模拟 100 个独立用户；
3. 抢单业务耗时（毫秒级）远小于锁 TTL（10s），未触发"锁超时后释放返回 false"路径，
   该路径语义已由代码与 TTL 演示覆盖，未做端到端演练。

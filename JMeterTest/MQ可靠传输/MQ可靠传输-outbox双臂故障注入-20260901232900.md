# MQ可靠传输-outbox双臂故障注入-20260901232900

## 假设与可量化判据（跑前登记）

- **假设 A（broker 故障）**：MQ 不可达期间写入发件箱的高价值消息零丢失；
  broker 恢复后轮询中继自动补发，`ch_outbox` 全部 `status=1`（confirm 闭环），
  `ch_log` 恰好新增对应行数。
- **假设 B（应用崩溃）**：发件箱行随业务库持久化，`docker kill` 后未发送的
  消息在应用重启后由中继补发，同样零丢失。
- **幂等假设**：重复投递撞消费端唯一键 `uk_log_event(log_type, log_target_id, create_time)`
  被当作已消费吸收，消息正常 ACK 不进 DLQ，不产生重复落库。
- **可量化判据**：双臂各注入 20 条 → 最终送达行数 = 40、丢失 = 0、
  `status=1` 行数 = 40；人为重复 2 条 → `ch_log` 行数不变、DLQ 深度 0。

## 实验环境

- 合并后 master（68ccffd），docker compose：应用容器 8080、RabbitMQ 4、
  MySQL 8.4（ch_outbox/ch_log 容器内）。
- 消息通路：`ch_outbox`（事务内写）→ OutboxRelay 5s 轮询 → `campushub.log`
  交换机 → `campushub.log.queue` → LogConsumer 幂等落库 `ch_log`。
- 消息体：LogEvent JSON，Arm A 目标 ID 9900000001-9900000020，
  Arm B 9900000021-9900000040，重复臂复用 A-01/A-02 的 payload。

## 预期 vs 实测

### Arm A：broker 故障（docker compose stop rabbitmq）

| 阶段 | outbox 状态 | 计数证据 |
|---|---|---|
| 注入 20 条（broker 已停） | status0=20 | `COUNT=20` |
| 宕机期间轮询 | 持续 status0 | `avg_retry=7.0`（每 5s 一轮重发失败，静默重试） |
| broker 恢复 15s 后 | **status0=0, status1=20** | confirm 全量回执 |
| 消费端 | — | `ch_log` 目标区间行数 = **20**（预期 20，丢失 0） |

### Arm B：应用崩溃（注入 20 条后立即 docker kill）

| 阶段 | outbox 状态 | 计数证据 |
|---|---|---|
| 注入后 kill（未及发送） | status0=20 随 MySQL 持久化 | 重启后行数不变 |
| 重启后（补齐拓扑修复） | **status0=0, status1=20** | 中继首轮即全部补发 |
| 消费端 | — | `ch_log` = **20**（预期 20，丢失 0） |

### 幂等臂：人为重复投递 2 条

- outbox 2 条重复 payload 均被消费并 confirm（`status1=2/2`）；
- `ch_log` 对应目标 ID 行数保持 **2**（零重复落库）；
- `campushub.log.queue` / `campushub.log.dlq.queue` 深度均为 0（重复被正常 ACK）。

**总判据：提交 40 → 送达 40 → 丢失 0；重复 2 → 吸收 2 → 队列零积压。全部满足。**

## 实验中发现并修复的两个真实缺陷

1. **调度线程池饿死（严重）**：默认单线程调度器下，浏览量刷库任务（对百万行
   ch_post 逐条 UPDATE）长期占用 `scheduling-1`，发件箱中继 5s 轮询被饿死
   （72s 内 retry_count=0，线程转储证实）。修复：`spring.task.scheduling.pool.size: 4`。
   修复前 broker 宕机臂无法进入"轮询重试"阶段——该缺陷会让可靠传输在真实
   负载下退化为"不重发"，属于本次测试最有价值的发现。
2. **帖子互动拓扑声明丢失（严重）**：057b681 移除误入订单分支的互动拓扑后未补回，
   干净 broker 上 `campushub.post.interaction.queue` 不存在，
   `missingQueuesFatal` 导致应用启动即失败退出。修复：RabbitMqConfig 补齐
   互动交换机/队列/DLX/DLQ/绑定声明（与日志拓扑同风格）。

两次修复后双臂复测均满足判据。原始错误现象与解法同步登记于同目录 error.md。

## 结论

confirm 回执 + 发件箱事务内写 + 轮询补发 + 消费幂等的四段防御，在 broker 宕机、
应用崩溃、消息重复三种故障注入下均满足"至少一次不丢"语义：40/40 送达、0 丢失、
重复全吸收、DLQ 零积压。RabbitMQ 可靠传输链路在合并后验证成立。

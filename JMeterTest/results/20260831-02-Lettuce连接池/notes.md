扫描轮两点必须注记（均不改变确认级结论）：

1. **cold/mixed 扫描轮为温读失真**：扫描用 seg 段文件轮内循环复用，首遍之后缓存命中，故扫描 QPS 接近 hot 水平（~4100-4400），不能作为 cold/mixed 极限。确认级改用 fresh 段单遍不循环，misses/req=1.000 证实真冷。hot-single 因压前已预热不受影响。
2. **宿主机漂移**：pool-on hot-single scan-150（23:54）= 5505.6，而确认轮 p2（00:27）= 4382.1，同 arm 同 150 线程相隔 33 分钟 -20%；同窗口内 pool-off scan-150（00:18）= 4181.6 与确认轮（00:24）= 4239.0 一致。推测：pool-off 瓶颈在共享单连接（对 CPU 频率漂移不敏感），pool-on 瓶颈转移至 CPU（对持续满载降频敏感）。

### 池生效机制证据（INFO clients）

- pool-off：压测窗口 connected_clients = **2**（1 共享连接 + redis-cli），判据 1~2 PASS

## 池容量红线事件（判据约定内调参）

初版 max-active=16 压测触发借取超时（`NoSuchElementException: Timeout waiting for idle object`），按判据"借取超时=红线，调参重测并记录"处理：16→64 仍触发→**192/64/4/100ms** 后消除。最终参数写入 application-dev.yml，两 arm 共用同一重建 jar（23:47:49，启动参数 `--campushub.redis.pool-enabled` 切换）。复测后双 arm err 日志 0 字节，全部确认轮错误率 0。

## 结论

- **预期 vs 实测（逐条判据）**：
  - hot-single：pool-on ≥ 1.5 × pool-off → 实测 1.034（配对）/ 最高 1.27（健康扫描窗口）→ **未达**
  - mixed-80-20：pool-on ≥ 1.3 × pool-off → 实测 1.078 → **未达**
  - cold-all：pool-on ≥ pool-off → 实测 0.923（-7.7%）→ **未达**（回退）
  - 错误率 = 0 → **PASS**（全部确认轮）；借取超时 → 调参后 **PASS**
  - 命令数守恒（3 / 3.2 / 4）→ **PASS**
  - MySQL 卸载守恒（0 / ~0.15 / 1）→ **PASS**
  - 池生效机制证据（2 vs 65 连接）→ **PASS**
- **差异归因**：机制证据完整排除实现 bug，判据未达属于**模型错误**——实验 01 将"瓶颈主因"归于共享单连接串行化，实测表明在本机形态（QPS 4000~5500 区间）单连接只是构成一个**上限**（pool-off 自 30 线程起即平台化，4087→4182 不随线程增长；pool-on 30→200 持续爬升 4436→5547，+25%），但在确认窗口可达的负载下并非主要约束；真正的复合上限在 Tomcat / 宿主机 CPU。cold-all 回退 -7.7% 的归因：cold 瓶颈在 MySQL 点查回源路径，池化不减少 MySQL 工作量，反而引入借还开销与更高并发的回源冲击（p99 87ms→159ms，并发到达更陡）。
- **判据关闭**：1.5×/1.3× 假设关闭（两种口径下均未达，结论稳健）。
- **下一步动作**：
  1. `pool-enabled` 默认保持 false；本机形态下开启收益不稳定且 cold 场景回退，如开启需保证 max-active ≥ 并发（192 实证无借取超时）。
  2. 瓶颈定位转向 Tomcat 线程池 / 日志 I/O（下一实验假设来源）。
  3. 若需复测池化上限，须在持续满载预热后的稳定窗口（或跨日多次配对）进行，避免本实验暴露的 ~20% 宿主机漂移污染绝对值。
